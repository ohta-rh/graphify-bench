# Phase 12: 三つの軸をさらに削る（`lean-tools` / `few-turns` / `haiku-nosub` / `all-in`）

計測日 2026-09-02 / Claude Code **2.1.258** / corpus `corpus-v1`（code-45） /
main model は arm により `claude-sonnet-5` または `claude-haiku-4-5`。
前段は [`LEVERS.md`](./LEVERS.md)（Phase 10–11）。

---

## 1. 出発点

Phase 11 までで最も安かった条件は `effort-low-nosub`
（`--effort low` + `--disallowedTools Agent`）である —
uncached_all 中央値 142,566 トークン、コスト中央値 $0.098、正答率 84.4%。
索引もツールも足さない、ただ削るだけの条件が、11 フェーズ・680 ランを通じて
最も安かった。

ではその先はどこを削れるのか。残っているコストは大きく三つに分解できる。

| # | 軸 | 何を削るか | Phase 12 のアーム |
|---|---|---|---|
| 1 | **ターンあたりの固定費** | 毎ターン再送される system prompt + ツール定義 | `lean-tools` |
| 2 | **ターン数** | 探索の往復回数そのもの | `few-turns` |
| 3 | **モデル単価** | Sonnet 5 → Haiku 4.5 | `haiku-nosub` |
| — | 全部 | 上の三つを同時に | `all-in` |

三つとも「エージェントに何かを与える」条件ではない。Phase 2–9 が測った
索引系がすべて外れた以上、残る問いは「削り方をどこまで積めるか」である。

## 2. 条件設計

`bench/conditions.ts` に 4 アームを登録した。corpus はすべて v1、
比較対象は `effort-low-nosub`（Phase 11 の最良条件）と、
Haiku 側は `haiku-baseline`（Phase 6）である。

| condition | overlay | model | effort | CLI 差分 |
|---|---|---|---|---|
| `lean-tools` | `overlays/baseline` | `claude-sonnet-5` | low | `--tools Read,Grep,Glob,Bash,Edit` + `--disallowedTools Agent` |
| `few-turns` | **`overlays/few-turns`** | `claude-sonnet-5` | low | `--disallowedTools Agent` |
| `haiku-nosub` | `overlays/baseline` | **`claude-haiku-4-5`** | （既定 high、下記 §3.2） | `--disallowedTools Agent` |
| `all-in` | **`overlays/few-turns`** | **`claude-haiku-4-5`** | （既定 high） | `--tools ...` + `--disallowedTools Agent` |

各アームが「名乗った軸ちょうど」であることは `bench/conditions.test.ts` の
`phase 12 lean arms` ブロックで、既存アームの spec と突き合わせて検証している。
`all-in` は他の三つの**厳密な合併**であり、第四の差分を含まない。

### 2.1 `few-turns` — CLAUDE.md は baseline の**バイト単位の拡張**

`overlays/few-turns/CLAUDE.md` は `overlays/baseline/CLAUDE.md` の全文が
そのまま先頭に来て、その後ろに `## Working economy` 節が 1 つ足されているだけである
（テストが `startsWith` で検証している）。追記した内容は次の 5 点で、
いずれも**手数の使い方**の話であり、解答フォーマット契約には一切触れていない。

- `Grep -n`（または `Glob`）で場所を特定してから読む。中身を見るためにファイルを開かない
- 行番号が分かったら `Read` の `offset` / `limit` で範囲だけ読む
- 互いに独立したツール呼び出しは 1 ターンにまとめて出す
- 一度読んだものを読み直さない
- 証拠が十分になった時点で答える

契約部分を 1 バイトでも書き換えれば、測っているものが「ターン数」から
「グレーダに渡す入力」に変わってしまう。それを防ぐのが上記のテストである。

### 2.2 `lean-tools` — なぜ `--tools` であって `--allowedTools` ではないのか

§3.1 で実測したとおり、リクエストからツール定義そのものを消すのは
`--tools`（組み込みセットを**置き換える**許可リスト）だけである。
`--allowedTools` は権限フィルタで、ツールはモデルに提示されたまま残る。
`Edit` を残したのは `fix` カテゴリがコーパスのテスト実行で採点されるからで、
Edit のないアームは構成上 0/9 になり、自分の設定ミスを測るだけになる。

`--disallowedTools Agent` は `--tools` の許可リストに `Agent` が無い時点で
冗長だが、`claude.argv` を見たときに `effort-low-nosub` からの系譜が読めるよう
残してある。

## 3. 機構の検証（本計測の前に実施）

### 3.1 `--tools` は本当にツール定義を消すのか

空ディレクトリ・1 語のプロンプト・`claude-haiku-4-5`・`--max-turns 1` で
`claude -p` を回し、**キャッシュ済みプレフィクス全体**
（`cache_creation_input_tokens` + `cache_read_input_tokens`）を比較した。
キャッシュが温まると同じ内容が creation から read へ移るので、
`cache_creation` 単独では比較にならない — これがこの検証の一番の落とし穴である。

| 呼び方 | プレフィクス合計 | creation | read |
|---|---|---|---|
| 既定（フラグなし） | 21,138 | 7,356 | 13,782 |
| `--disallowedTools Agent` | 18,235 | 6,766 | 11,469 |
| `--tools Read,Grep,Glob,Bash,Edit` | **18,854** | 4,746 | 14,108 |
| 同上（再実行） | 18,858 | 4,750 | 14,108 |
| `--tools Read` | 14,143 | 14,143 | 0 |
| `--tools ""` | **13,457** | 13,457 | 0 |

`--tools ""` の 13,457 が system prompt だけの床であり、ここまで落ちること自体が
「`--tools` はスキーマを実際に落としている」ことの証明である
（既定との差 7,681 トークンが組み込みツール定義の総量）。

**ただし、この実験にとって重要なのは 3 行目である。** 5 ツールに絞ると固定
プレフィクスは 18,854 で、`--disallowedTools Agent` だけの 18,235 より
**約 620 トークン大きい**。つまり `lean-tools` はこのホストにおいて
固定費レバーではない。

なぜ増えるのかは**未検証の仮説**であり、事実として扱ってはならない:
既定では一部のツールが deferred（名前だけ提示され、スキーマは要求時に展開される）
状態で載っており、`--tools` で明示すると指定分が完全なスキーマで載るため、
という説明が上の 6 行と矛盾しない。5 ツールで 5,397 トークン（= 18,854 − 13,457）を
使うのに既定の全ツールが 7,681 トークンしか使わない、という内訳がその根拠である。
確定させるには API リクエスト本体を取る必要があり、本計測ではそこまでしていない。

したがって `lean-tools` の主張は「固定費が減る」ではなく
「**手数の選択肢が減ることで挙動が変わるか**」に置き換わる。
測る前に主張が変わったので、そのままそれを測った。

### 3.2 Haiku 4.5 は `--effort` を尊重するか — しない

`--effort` を付けてもエラーにはならないので、無視されているかどうかは
thinking トークンを見るしかない。同一プロンプト（`--tools ""`）で:

| model | `--effort` | thinking トークン |
|---|---|---|
| `claude-haiku-4-5` | low | 202 |
| `claude-haiku-4-5` | max | 172 |
| `claude-haiku-4-5` | （なし） | 690 |
| `claude-sonnet-5` | low | **0** |
| `claude-sonnet-5` | max | **192** |

Sonnet では low → max が 0 → 192 と単調に動くのに対し、Haiku では
low が max より**多い**。単調性がなく、フラグ無しが一番大きい。
公式ドキュメント（`model-config.md`）も Haiku を effort 対応モデルとして
挙げていない。**Haiku は `--effort` を尊重しない**と判定した。

その帰結として、Haiku 系 2 アームには `--effort` の override を**置かなかった**。
LEVERS.md §2.1 が書いているとおり、このリポジトリで唯一致命的な失敗モードは
「`run.meta.json` に、モデルに届かなかった treatment が記録されること」である。
`haiku-low-nosub` という名前は Director の指示にあったが、`low` が適用されない以上
その名前は嘘になるので、**`haiku-nosub` に改名した**。ハーネス既定（`high`）を
そのまま受けるのは `haiku-baseline` と同じで、この一致が
`haiku-nosub` − `haiku-baseline` を単一変数の比較にしている。

### 5.3 軸ごとの読み

**軸 1（ターンあたり固定費）— 空振り。** `lean-tools` は
`effort-low-nosub` に対してトークン・コスト・ターン数のすべてで CI がゼロを跨いだ。
これは §3.1 の事前計測どおりで、5 ツールの許可リストは固定プレフィクスを
**縮めない**（むしろ約 620 トークン増える）以上、削減が出ないのが正しい。

ただし挙動は明確に変わった。ツールを絞ると探索が `Bash`（=シェルの grep）から
専用の `Grep` に移る:

| arm | Grep | Read | Bash | Glob | Edit |
|---|---|---|---|---|---|
| `effort-low-nosub` 系の非制限アーム（`few-turns`） | 0 | 124 | **402** | 0 | 20 |
| `lean-tools` | **236** | 238 | 72 | 4 | 20 |
| `haiku-nosub` | 0 | 616 | **746** | 0 | 22 |
| `all-in` | **530** | 530 | 220 | 80 | 22 |

許可リストを渡すと `Grep` が完全なスキーマで提示されるので選ばれやすくなる、
というのが §3.1 と同じ仮説での説明だが、確定はしていない。確定しているのは
**探索の主力が `Bash` から `Grep` に移った**という観測のほうである。
コストは変わらないが `locate` は 7/9 → 8/9 に上がり、`fix` は 9/9 → 7/9 に落ちた。
**差し引きゼロで、この N では区別できない。**

**軸 2（ターン数）— レバーは効いたが、量が足りない。** `few-turns` は
ターン中央値 6 で `effort-low-nosub` と同じ、対応のある差は −0.53 ターン
[−1.44, +0.33] でゼロを跨ぐ。コストも −5.2% でゼロを跨ぐ。
**正答率は 38/45 で `effort-low-nosub` と完全に同じ**（カテゴリ別も一致）。
つまり指示は害を与えなかったが、`--effort low` + サブエージェント禁止の時点で
ターン数はすでに 6 まで落ちており、**プロンプトで削る余地がほとんど残っていなかった**。
このアームの正しい読み方は「turn-economy の指示は無効」ではなく
「**すでに 6 ターンまで削られた条件に対しては無効**」である。

**軸 3（モデル単価）— トークンで支払い直すだけ。** `haiku-nosub` は
`effort-low-nosub` に対してトークン +177%、ターン +8.8、それでコストは同じ
（CI がゼロを跨ぐ）。Haiku は単価が約 1/3 だが、同じ仕事に 2.8 倍のトークンと
2.2 倍のターンを使うので、ちょうど相殺される。さらに wall は 15.7 s → 55.3 s と
**3.5 倍遅い**。`haiku-nosub` − `haiku-baseline` が全指標でゼロを跨いだのも重要で、
**Sonnet で最強だった「サブエージェント禁止」は Haiku では効かない** —
`haiku-baseline` はそもそもほとんど委譲しないからである。

**`all-in` — レバーは Haiku 上でも合成する。** `all-in` − `haiku-nosub` は
トークン −9.6%、コスト −7.3% でどちらも CI がゼロを跨がない。
つまり `--tools` と turn-economy CLAUDE.md は、Sonnet 上では検出できなかった
効果を、**Haiku 上では出す**。弱いモデルほど探索の無駄が大きく、削る余地が
残っているから、という向きで一貫している。
それでも `effort-low-nosub` には勝てない: コストは −14.2% だが CI はゼロを跨ぎ、
正答率は 75.6% で 4 タスク下、wall は 2.8 倍である。

### 5.4 精度の代償

| arm | locate | reference | explain | impact | fix | 計 |
|---|---|---|---|---|---|---|
| `effort-low-nosub` | 7/9 | 9/9 | 9/9 | 4/9 | 9/9 | 38/45 |
| `lean-tools` | **8/9** | 9/9 | 9/9 | 4/9 | 7/9 | 37/45 |
| `few-turns` | 7/9 | 9/9 | 9/9 | 4/9 | 9/9 | **38/45** |
| `haiku-nosub` | **8/9** | 9/9 | 9/9 | **3/9** | 8/9 | 37/45 |
| `all-in` | 6/9 | 7/9 | 8/9 | **5/9** | 8/9 | 34/45 |

`all-in` の損失は 1 カテゴリに集中しておらず、`locate`・`reference`・`explain`
に薄く広がっている。これは effort レバーの失敗の仕方（`locate` に全部乗る）とは
別種で、**モデルを落としたことによる一般的な劣化**の形である。
n=45・反復 1 回なので 4 タスクの差は有意ではないが、
「安いほうに寄せると精度が薄く均一に削れる」という向きは
`haiku-baseline`（36/45）とも整合する。

### 5.5 残ったトークンはどこへ行くのか

レポート §11（`--token-decomposition`）が
`uncached_all` を **fixed = `first_turn_cache_creation` × `num_turns`**（毎ターン
再送される system prompt + ツール定義）と **moving = 残り**（ファイル内容・
ツール結果・推論）に割る。中央値:

| arm | uncached_all | turns | first-turn | fixed | moving | fixed 比 |
|---|---|---|---|---|---|---|
| `baseline` | 260,561 | 5 | 10,357 | 49,825 | 223,347 | 16.8% |
| `effort-low-nosub` | 142,566 | 6 | 9,515 | **57,000** | **93,247** | **35.3%** |
| `lean-tools` | 151,221 | 6 | 6,668 | 39,828 | 108,568 | 23.7% |
| `few-turns` | 159,886 | 6 | 9,871 | 59,052 | 100,783 | 36.2% |
| `haiku-nosub` | 308,582 | 13 | 7,417 | 81,642 | 226,940 | 26.5% |
| `all-in` | 200,484 | 13 | 5,680 | 73,671 | 133,723 | 27.0% |

**これが Phase 12 の一番使える数字である。** `effort-low-nosub` では
トークンの **35%** が「タスクとは無関係の、ただセッションが 6 ターン続いた費用」
であり、`baseline`（16.8%）の 2 倍を超える。理由は単純で、レバーは moving
（223k → 93k、−58%）だけを削り、fixed は削らなかったからである。
削れば削るほど、残りに占める固定費の割合は上がる。

そして固定費は**プロンプト側からは動かせない**。`few-turns` は fixed 比が
36.2% でむしろ最大であり、`lean-tools` は first-turn の creation を
9,515 → 6,668 に落としているように見えるが、これは §3.1 のとおり
**キャッシュの温まり方の差であって、リクエストが小さくなったわけではない**
（creation + read の合計で見ると `lean-tools` のほうが大きい）。
`first_turn_cache_creation` 列を「リクエストの大きさ」として読んではいけない
というのが、この列を持つレポートを読む上での最大の注意点である。

したがって次に効く可能性があるのは、**ターン数そのものを 6 から更に減らすこと**
だけである。fixed はターン数に線形なので、6 → 3 なら 28k トークンが消える。
`few-turns` はそれを指示で試みて −0.53 ターンしか動かせなかった。
プロンプトではなく機構（1 ターンあたりの並列ツール呼び出し数を強制する、
あるいは `--max-turns` を絞る）を変える実験が、この先の唯一の残り道である。

## 6. 判定

**軸 1（ツール制限）は不採用。** `--tools` は確かにスキーマを消すが、
5 ツールの許可リストは固定プレフィクスを**増やす**（§3.1）。
測定結果もトークン・コスト・ターンのすべてで CI がゼロを跨いだ。
変わったのは挙動（`Bash` grep → `Grep`）だけで、精度は `locate` +1 / `fix` −2 の
差し引きゼロである。**「ツールを絞れば固定費が減る」は、このホストでは誤りである。**

**軸 2（ターン数の指示）は不採用 — ただし「効かない」ではなく「もう余地がない」。**
`few-turns` は正答率を 1 タスクも落とさずに（38/45、カテゴリ別まで同一）
コストを 5.2% 下げたが、CI はゼロを跨ぐ。`--effort low` +
サブエージェント禁止がすでにターン中央値を 6 まで落としており、
プロンプトで削れる往復が残っていなかった。**害はないので、指示として
入れておくことに反対する理由もない** — ただし削減を主張してはいけない。

**軸 3（モデル単価）は不採用。** Haiku は単価 1/3 の代わりにトークンを 2.8 倍、
ターンを 2.2 倍、wall を 3.5 倍使うので、コストはちょうど相殺されて
`effort-low-nosub` と同じになり、精度だけが落ちる。Phase 6 の `haiku-baseline`、
Phase 10 の `haiku-explore` と合わせて、**このリポジトリで「弱いモデルに探索を
やらせる」形の条件は 3 回とも同じ結論に着地した**: 安いモデルは、安さを
食い潰すほど非効率に探索する。

**`all-in` は「最安の中央値」だが「最良の条件」ではない。** コスト中央値 $0.081 は
全計測を通じて最小であり、`baseline` に対しては −51.8%（CI はゼロを跨がない）。
だが `effort-low-nosub` に対する −14.2% は CI がゼロを跨ぎ、正答率は
84.4% → 75.6%、wall は 2.8 倍である。**推奨条件は依然として
`effort-low-nosub` のままである。**

**一つだけ新しく分かったこと。** `all-in` − `haiku-nosub` は
トークン −9.6%・コスト −7.3% で、どちらも CI がゼロを跨がない。
`lean-tools` と `few-turns` は Sonnet 上では何も動かさなかったのに、
Haiku 上では動いた。**削るレバーの効き目はモデルの無駄の量に比例する** —
すでに効率的な実行系に対しては、削る指示はもう何も残っていない。

**12 フェーズ・860 ラン後の総括は Phase 11 から変わらない。**
このリポジトリで最も安い実用条件は、索引もツールも足さず、
`--effort low` と `--disallowedTools Agent` の二つだけを掛けた条件である。
Phase 12 が足したのは、その先が**なぜ**行き止まりなのかという説明である:
残ったトークンの 35% はセッションを維持しているだけの固定費で、
それはプロンプトからもツール許可リストからも動かせない。
