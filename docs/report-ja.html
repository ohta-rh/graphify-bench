graphify-bench · 2026-09-02 · graphify vs 素の Claude Code

graphify を入れた Claude Code は、素の Claude Code より安くならなかった。

同じコードベース、同じ 65 問、同じモデル、同じ上限で、graphify あり・なしを 1 対 1 で走らせた。graphify の側には graphify install --project が入れるものをそのまま載せている。CLAUDE.md の指示、Read と Grep に割り込む hook、skill、事前構築したグラフ。

三行で言うと

  1. Sonnet 5 がコードを扱う限り、graphify は何も減らさない。トークンもコストも差が検出できず、ターンは 5 → 9 に増え、正答率は 6 ポイント下がった。
  2. 効くのは二つの場面。探索が下手なモデル（Haiku 4.5）ではトークン −25%。要件定義書・設計書とコードを横断する質問ではコスト −30%、正答率 +10 ポイント。特に「仕様と実装の矛盾を探せ」で 4/4 対 2/4。
  3. graphify は「読む代わり」ではなく「読む前の一手」になっていた。query が返すのはノードとエッジのラベルで、エージェントは結局そのファイルを読む。素の Claude Code はそもそも探索をサブエージェントに任せていて、削る余地が索引側になかった。

graphify が勝った場面

Haiku 4.5。探索が下手なモデルは素のままだと 50 万トークン使う。graphify を入れると 33 万で、正答率は 80% → 82%。索引が「弱い探索役の補助輪」として機能した唯一のモデル。先行研究（arXiv:2608.13568、LSP は Haiku で −26%、Sonnet で +118%）と同じ構図。

中で何が起きていたか

素の Claude Code は最初から読んでいない。45 ラン中 23 ランで探索を Explore サブエージェントに委譲し、要約だけを受け取る。graphify が削るはずの「無駄な全文読み」は存在しない。graphify を入れると委譲は 0 になり、主セッションが自分で query して自分で読む。

query は答えを返さない。graphify query の出力はノードとエッジのラベルと行番号（既定 2,000 トークンで打ち切り）。コードそのものではないので、エージェントはそのファイルを Read する。Read は 68 回から 191 回に増えた。網羅型の問い（全部列挙せよ）では打ち切りが致命的で、結局 grep で確認する。

hook が Read のたびに割り込む。graphify の PreToolUse hook は Read と Grep のたびに「先に query しろ」という文言をコンテキストに再注入する。1 回の Read に約 60 ms の税もかかる（素の Read は 6 ms、query は 294 ms）。

strict モードは一度も発火しなかった。「最初の生 Read をブロックする」設定を 65 ラン試したが 0 回。CLAUDE.md が先に query させるため、graphify 自身が 30 分間ブロックを無効化する。ノブとして死んでいる。

使われなかった機能。255 ランの graphify 側で呼ばれたのは query、explain、path だけ。affected（影響範囲の逆引き）、god-nodes、save-result、reflect（セッション間記憶）は 0 回。影響範囲タスクで負けたのは、それ用のコマンドが使われなかったからでもある。

graph.json の直読み。hook は graphify-out/ 配下を守らないので、4.6 MB のグラフ本体を Read したランが 145 ラン中 10 ラン。

「70 倍」との差

graphify 自身の graphify benchmark は「クエリ出力のトークン ÷ コーパス全文のトークン」を計算している。計算は正しいが、全文を読むエージェントは存在しない。周辺のブログが引用する 70x や 79x はこの系譜で、実セッションの数字ではない。今回の実セッションでは、コードで 1.0 倍、文書で 1.3 倍程度、Haiku で 1.5 倍。

公平さのために書いておくこと

  • graphify 側の腕には、グラフだけでなく skill の文章、CLAUDE.md の指示、hook の注意書きも載っている。それが graphify install --project でユーザーが実際に得るものなので、差し引いていない。
  • claude -p の結果 JSON の usage は主セッションだけを数える。それで見ると graphify は +290% 悪く見えるが、素の Claude Code がサブエージェントに使ったトークンが抜けているだけ。modelUsage を全モデルで合算した数字で比較している。
  • 削減の主張は両腕が正解したタスクだけで行っている（iso-accuracy）。正答率が違う腕同士の削減率は意味を持たない。
  • 反復は 1 回、コーパスは 1 つ。信頼区間はタスク間のばらつき。方向を信じて、大きさは幅を持って読む。

判定

入れる理由がある
  • Haiku など、探索が弱いモデルで動かす
  • 要件定義書・設計書が ID でコードを指していて、その横断を聞く
  • 仕様と実装の矛盾を探させる
  • 人間がコードベースを俯瞰する（レポートと可視化は 4.6 秒、無料）
入れる理由がない
  • Sonnet 5 以上でコードだけを扱う
  • 「呼び出し元を全部」「変えたら直す場所を全部」型の調査が中心
  • grep で当たりが付く規模のリポジトリ
  • トークン削減が目的（コードでは減らない）

参考。同じハーネスで、索引を足さずに設定だけ変えた腕も測った。--effort low --disallowedTools Agent で、素の Claude Code 比トークン −37%、コスト −42%、正答率同等、時間半分。トークンを減らしたいだけなら、graphify よりこちらが確実に効く。詳細は README と results/levers/REPORT.md。

どう測ったか

被験コードは Taskflow、この計測のために生成したオリジナルの Next.js 16 アプリ（477 ファイル、4.1 万行、テスト 617 本、全ルート起動確認済み）。学習データに無いものを使うのは、モデルが「知っていた」のか「索引で分かった」のかを切り分けるため。文書版（corpus-v2）は要件・設計・ADR・API・DB・画面・テスト・運用の 139 本を足し、12 か所に意図的な矛盾を仕込んである。

各ランは corpus の新品コピーに条件ごとの overlay を重ね、claude -p --output-format json を同じ上限（effort high、60 ターン、$4）で実行する。graphify の memory/ と LESSONS.md はランごとに消えるので、セッション間の持ち越しは無い。正答は機械キー（ts-morph で導出）、注入バグのテスト赤→緑、目隠しした Haiku の採点で判定。
