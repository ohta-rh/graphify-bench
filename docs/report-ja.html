graphify-bench · 2026-09-02 · graphify vs 素の Claude Code

graphify を入れても、Sonnet 5 は安くならない。安くしたのは、素の Claude Code のフラグ二つだった。

同じコードベース、同じ問題、同じモデル、同じ上限で、graphify あり・なしを 1 対 1 で走らせた。graphify 側には graphify install --project が入れるものをそのまま載せた。数字は「graphify を入れたときの増減」で読める。マイナスが節約、プラスは余計に使った。

graphify が勝つ二つの場面

探索が下手なモデル

Haiku 4.5 は素のままだと 1 問 50 万トークン使う。graphify を入れると 33 万で、正答も 1 問増える。索引が「弱い探索役の補助輪」として働く。先行研究（LSP は Haiku で −26%、Sonnet で +118%）と同じ構図。

設計書とコードを行き来する質問

要件定義書・設計書・ADR など 139 本を足したコーパスで、「この領域で仕様と実装が食い違っている文書は」と聞くと、graphify は 4 問中 4 問を当て、素の Claude Code は 2 問。費用は 3 割安い。文書が ID でコードを指していることが条件。

中で何が起きていたか

素の Claude Code は最初から読んでいない。探索を Explore という別セッションに任せて、要約だけ受け取る。graphify が削るはずの「無駄な全文読み」がそもそも無い。

graphify は「読む代わり」ではなく「読む前の一手」。graphify query が返すのはノードとエッジのラベルと行番号で、コードそのものではない。エージェントは結局そのファイルを読む。読む回数は 68 回から 191 回に増えた。

hook が読むたびに割り込む。Read と Grep のたびに「先に query しろ」という文言がコンテキストに再注入され、1 回の Read に約 60 ms の税がかかる（素の Read は 6 ms）。

使われなかった機能が多い。255 ランで呼ばれたのは query、explain、path だけ。影響範囲を逆引きする affected、セッション間記憶の save-result と reflect は 0 回。「最初の生 Read をブロックする」strict モードも、CLAUDE.md が先に query させるせいで一度も発火しなかった。

「70 倍」との差

graphify 自身の graphify benchmark は「クエリ出力のトークン ÷ コーパス全文のトークン」を計算している。計算は正しいが、全文を読むエージェントは存在しない。実セッションでの節約は、コードで 0 倍、文書で 1.2 倍、Haiku で 1.3 倍程度。

設定の効果はどれだけ確かか

「安くなる」と「速くなる」の主張を、素の Claude Code に対する増減で示す。マイナスが節約、左に伸びるほど良い。薄い横棒は 95% の幅で、ゼロ線をまたがなければ本物。

素の Claude Code との差（マイナスが節約）

費用と使用量（トークン）は 45 問の合計に対する増減率で、幅はタスクをブートストラップした 95% 区間。時間は中央値の差で、幅は出していない。

時間は effort のもの、節約はサブエージェント禁止のもの。graphify はどちらでもない

effort を high から low に落とすと、サブエージェントの有無にかかわらず時間が半分になる（29.5 → 16.2 秒、33.5 → 15.7 秒）。考える量が減るからで、思考トークンの比率は 37% から 16% に落ちる。

サブエージェントを止めても時間は減らない。並列で探索していたものを、主セッションが一人で順にやるようになるから、effort high では 4 秒遅くなる。その代わり、別セッションを立ち上げる固定費が消えるので費用は 3 割減る。

effort low で落とした 2 問（場所特定）は、サブエージェントを止めると戻る。主セッションが自分で探すようになって、探索役に任せていた見落としを拾い直す。

graphify は、素の Claude Code がすでに使っていない「無駄な全文読み」を削ろうとして、代わりにターンを増やした。設定のほうは、素の Claude Code が実際に使っている資源（別セッションの固定費と思考トークン）を削っている。効き方の差はそこにある。

判定

Sonnet 5 以上でコードだけを扱うなら、graphify を入れる理由がない。安くしたいなら --disallowedTools Agent、速くしたいなら --effort low。両方掛けると費用はほぼ半分、時間も半分、精度そのまま。graphify はこのどれにも届かない（両フラグ比で費用 2 倍、時間 2.4 倍、正答 −3）。

graphify を入れる価値があるのは、Haiku で動かすとき、または設計書が ID でコードを指していてその横断を聞くとき。人間がコードベースを俯瞰する道具としては、4.6 秒・無料で普通に使える。

気をつけること

  • graphify 側の腕には、グラフだけでなく skill の文章、CLAUDE.md の指示、hook の注意書きも載っている。それがユーザーが実際に得るものなので、差し引いていない。
  • claude -p の結果 JSON の usage は主セッションだけを数える。それで見ると graphify は 3 倍悪く見えるが、素の Claude Code が別セッションに使った分が抜けているだけ。全モデル合算で比べている。
  • 反復 1 回、コーパス 1 つ。幅はタスク間のばらつき。方向を信じて、大きさは幅を持って読む。正答の 2〜3 問差はノイズと切り分けられない。
  • 時間はざっくり。3 本並列で回した実測で、半減（29 → 16 秒）は信じてよいが、+4 秒や −0.5 秒は「変わらない」と読む。
  • 設定レバーは Sonnet 5 の話。Haiku 4.5 は --effort を無視する。これ以上は簡単には削れず、残る費用の 3 分の 1 はターンごとに固定のシステムプロンプトとツール定義を再送する分。ツールを絞る、節約を指示する、Haiku に落とす、はいずれも効かなかった。

どう測ったか

被験コードは Taskflow、この計測のために生成したオリジナルの Next.js 16 アプリ（477 ファイル、4.1 万行、テスト 617 本）。学習データに無いものを使うのは、モデルが「知っていた」のか「索引で分かった」のかを切り分けるため。文書版は要件・設計・ADR・API・DB・画面・テスト・運用の 139 本を足し、12 か所に矛盾を仕込んである。各ランは corpus の新品コピーに条件ごとの overlay を重ね、claude -p を同じ上限で実行。正答は機械キー、注入バグのテスト、目隠しした Haiku の採点で判定。生データは github.com/ohta-rh/graphify-bench。
