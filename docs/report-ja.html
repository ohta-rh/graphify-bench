索引を足してもトークンは減らない。減らしたのは、フラグ二つだった。

Claude Code に「コードの知識グラフ」を持たせれば探索が安くなる、という触れ込みを、実セッションで測った。graphify、MemPalace、公式の設定レバー。オリジナルの Next.js アプリと 65 問の採点付きタスクで、860 ラン。

三行で言うと

  1. Sonnet 5 にコードの索引は要らない。graphify（AST グラフ）も MemPalace（埋め込み索引）も、コードタスクではトークンを減らさなかった。MemPalace は明確に増やし、精度も落とした。
  2. 効いたのは設定だった。--effort low と --disallowedTools Agent を同時に掛けると、トークン −37%、コスト −42%、精度そのまま、時間は半分。
  3. 索引が効くのは二つの場面だけ。探索が下手なモデル（Haiku 4.5）と、要件定義書・設計書とコードを横断する質問。そこでは graphify が実際に安く、正確だった。

なぜ索引は効かなかったのか

素の Claude Code は、最初からあまり読んでいない。Sonnet 5 は 45 ラン中 23 ランで探索を Explore サブエージェントに委譲し、要約だけを受け取る。graphify が削るはずの「無駄な全文読み」が、そもそも存在しない。

索引は「読む代わり」にならず、「読む前の一手」になる。graphify query が返すのはノードとエッジのラベルと行番号で、コードそのものではない。エージェントは結局そのファイルを読む。ターン数は 5 から 9 に増え、hook の注意書きは Read のたびに再注入される。MemPalace は 16 KB のチャンクを返し、それをまた Read する。

網羅型の質問に、類似検索は答えられない。「この関数を呼んでいる全ファイル」という問いで MemPalace の精度が落ちた。上位 k 件の似たものを拾う仕組みは、辺を辿って全部を列挙する仕組みとは別物だ。

計測上の落とし穴が一つ。claude -p の結果 JSON の usage は主セッションだけを数える。それで見ると graphify は +290% 悪く見えるが、baseline がサブエージェントに使ったトークンが抜けているだけだった。modelUsage を全モデルで合算すると、差は消える。

文書のほうは、要件定義書・設計書・ADR など 139 本（26 万語）をコーパスに足し、REQ や DES の ID とコードを相互参照させた上で、「この領域で、仕様と実装が食い違っている文書はどれか」という問いを 12 か所の仕込んだ矛盾に対して出した。graphify は 4 問中 4 問を当て（F1 0.94）、素の Claude Code は 2 問（0.68）。コストは 29% 安い。graphify の本領は AST ではなく、文書とコードを結ぶ意味抽出のほうにあった。

ただし条件がある。文書がコードを明示的に指していること（ID や「Implemented by」）、そして質問が横断型であること。散文だけの Wiki を放り込んでも辺は引けない。

「70 倍削減」の正体

graphify 自身の graphify benchmark は、「クエリ出力のトークン ÷ コーパス全文のトークン」を計算している。計算は正しい。ただし全文を読むエージェントは存在しないので、比較対象が架空だ。周辺のブログが引用する 70x や 79x はこの系譜で、実セッションの数字ではない。

MemPalace はもう少し誠実で、過去に盛った数字を自分で撤回し、今の看板は会話記憶の recall ベンチだ。それはコーディングのトークンとは別の話で、実際コードでは 9 比較すべてで勝てなかった。

ほかに 13 候補を調べたが、実セッションで第三者が削減を確認した道具は一つもなかった。自己申告、合成推定、会話ベンチの転用、のいずれかだった。

推奨する設定

Sonnet 5 で、コードを扱うなら

claude -p "…" --effort low --disallowedTools Agent

baseline 比でトークン −37%、コスト −42%、正答率は 84% のまま、実時間は 29 秒 → 16 秒。二つの効果は重なるが（単純な和の 76%）、それぞれ単独より確かに安い。

  • サブエージェント禁止だけなら −29%、精度そのまま、+4 秒。小さい調査ならこれで十分。大きな改修調査では並列の利得が伸びるので、待ち時間とコストの好みで決める。
  • effort low だけだと同じくらい安いが、精度が 4 ポイント落ちる（locate 系で 2 問）。
  • これ以上は簡単には削れない。残るトークンの 35% は固定コンテキスト（システムプロンプトとツール定義）のターン毎再送で、ターン数以外では減らない。ツールを 5 個に絞っても差は出ず、「節約せよ」の指示はターンを 0.5 しか減らさなかった。
  • Haiku に落とせばコストはさらに −52% だが、精度が 76% に落ちてトークンは増える。安さと精度の交換にすぎない。

気をつけること

  • コーパス 1 つ、反復 1 回。信頼区間はタスク間のばらつきを見ているので、方向を信じて、大きさは幅を持って読む。
  • graphify 側の腕は、グラフだけでなく skill の文章と hook の注意書きも一緒に載っている。それが「ユーザーが実際に得るもの」なので差し引いていない。
  • graphify の strict モード（初回の生 Read をブロック）は 65 ラン中一度も発火しなかった。CLAUDE.md が先に query させるので、自分で自分を無効化する。affected、save-result、reflect といった機能も一度も呼ばれなかった。
  • Haiku 4.5 は --effort を無視する。

どう測ったか

被験コードは Taskflow、この計測のために生成したオリジナルの Next.js 16 アプリ（477 ファイル、4.1 万行、テスト 617 本、全ルート起動確認済み）。学習データに無いものを使うのは、モデルが「知っていた」のか「索引で分かった」のかを切り分けるため。

各ランは corpus の新品コピーに条件ごとの overlay（CLAUDE.md、hook、skill、事前構築したグラフや索引）を重ね、claude -p --output-format json を同じ上限で実行する。トークンは結果 JSON の modelUsage を全モデルで合算、正答は機械キー（ts-morph で導出）、注入バグのテスト赤→緑、目隠しした Haiku の採点で判定。トークン削減は両腕が正解したタスクだけで主張する（arXiv:2608.13568 の流儀）。
