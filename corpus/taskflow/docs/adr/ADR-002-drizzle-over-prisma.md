# ADR-002 — Use Drizzle ORM over SQLite rather than Prisma

## Status

Accepted. In force since the second week of the project. No migration off
Drizzle is planned; the repository layer under src/server/repositories/ is
now large enough (one repository per aggregate: issues, projects,
organizations, members, webhooks, activity, search, sessions) that a change
here would be a multi-week project, not a config swap.

## Context

The database decision was made alongside, and constrained by, the decision to
ship a fully offline, single-writer application backed by SQLite —
`better-sqlite3` version 13.0.3 is the actual driver in `package.json`. Given
SQLite as the engine, the ORM choice came down to two realistic options:
Prisma, which the team had used before, and Drizzle, which was newer but had
a SQLite-first story.

Three things pushed the decision away from Prisma specifically:

1. **A generated client versus a query builder.** Prisma's model is a schema
   file that runs a code generator to produce a client; that generator is a
   build step with its own cache invalidation semantics, and in an offline,
   no-external-services environment the team wanted one fewer thing that
   could silently go stale between a schema edit and the next `next dev`
   restart. Drizzle's schema files, under src/server/db/schema/ — one file
   per aggregate (`organizations.ts`, `members.ts`, `projects.ts`,
   `issues.ts`, `comments.ts`, `notifications.ts`, `activity.ts`,
   `billing.ts`, `webhooks.ts`, `users.ts`, plus the shared column helpers in
   `_shared.ts`), reassembled in `src/server/db/schema/index.ts` — are plain
   TypeScript that IS the runtime schema; there is no generation step, only
   `drizzle-kit` (0.31.10 in `package.json`) producing migration SQL from a
   diff against the previous schema.
2. **Query shape control for keyset pagination.** ADR-008 commits Taskflow to
   keyset (cursor) pagination on every list endpoint, which needs precise
   control over `WHERE (sort_col, id) > (?, ?)` predicates and composite
   ordering. Prisma's query API at the time made this awkward to express
   without dropping to raw SQL; Drizzle's `and()`/`or()`/comparison operator
   builders map onto exactly this shape, which is what
   `src/server/repositories/issue-repository.ts` and its siblings use
   directly.
3. **Thin runtime, single connection.** `better-sqlite3` is synchronous and
   in-process; Drizzle's SQLite driver wraps it without adding a connection
   pool or a query engine binary, which matters for an app that has to build
   and run without any network access. `src/server/db/client.ts` opens the
   one process-wide connection; `src/server/db/index.ts` is the only module
   that exports the typed `db` handle repositories import.

The trade-off the team accepted going in: Drizzle's tooling and community
were smaller in November 2025 than Prisma's, and the team would be writing
somewhat more SQL-adjacent code by hand (join conditions, migration review)
than Prisma's higher-level relational API would have asked for.

## Decision

All persistence goes through Drizzle. Schema is declared once, per aggregate,
under src/server/db/schema/; `src/server/db/schema/_shared.ts` defines the
common column helpers (timestamps, the `archived_at` soft-delete column used
by ADR-004, and the `org_id` foreign key pattern used by ADR-006) so every
table definition composes them rather than repeating column boilerplate.
Migrations are generated by `drizzle-kit` and applied by
`src/server/db/migrate.ts`; `src/server/db/seed.ts` is the offline fixture
loader used by local development and the test harness (`tests/helpers/db.ts`
opens a fresh in-memory or temp-file database per test run).

Repositories under src/server/repositories/ are the only code that imports
the Drizzle query builder or the schema modules directly. Nothing in
src/server/services/ or above touches `db` or a schema table object — a
service calls a named repository function (`issueRepo.findById`,
`webhookRepo.claimPendingDeliveries`) and gets back a plain typed row or
domain object, never a Drizzle query builder in flight. This split is the
same boundary ADR-013 describes for authorization: repositories own the SQL,
services own everything else.

## Consequences

**What this buys the team.** Migrations are inspectable SQL files, generated
from a TypeScript source of truth, with no generated client to keep in sync;
`next dev` and the test suite both start faster with no codegen step in the
loop. The query builder maps directly onto the keyset predicates ADR-008
needs, so `issue-repository.ts`'s `keysetPredicate(sort, cursor)` helper is a
few lines of comparison-operator composition rather than raw SQL string
interpolation. Because schema files are plain TypeScript, a reviewer diffing
a pull request sees the actual column change, not a regenerated multi-hundred
line client artifact.

**What it costs.** The team gave up Prisma's relational query API
(`include`/`select` graphs) and, with it, some convenience for fetching
nested data in one call; several repository functions do two or three
sequential queries where a single Prisma `include` might have done one round
trip, which is an acceptable cost only because `better-sqlite3` queries are
synchronous, in-process, and fast — there is no network latency to amortize
away by batching. The team also lost Prisma's more mature migration-diffing
UX; `drizzle-kit`'s diff has occasionally proposed a table-rebuild migration
for a change that should have been a plain `ALTER TABLE ADD COLUMN`, which
means every schema change to a table with meaningful data gets a manual
review of the generated SQL before it is applied — this is now a documented
step in the platform team's schema-change checklist, not an automated gate.
Onboarding cost is real too: new engineers who know Prisma from prior jobs
spend their first week or two relearning query composition patterns; Rin
Saito's post-mortem notes from the billing schema work in December 2025 flag
this explicitly as slower ramp-up than expected.

## Alternatives considered

**Prisma.** The default choice given team familiarity, rejected for the
codegen-step and keyset-pagination-ergonomics reasons above. Revisited
informally in February 2026 during the ADR-008 pagination work and rejected
again for the same reasons, this time with actual query examples in hand.

**Raw `better-sqlite3` with hand-written SQL and no ORM.** Gives maximum
control over every query but was rejected because it would have meant
hand-maintaining TypeScript row types alongside SQL strings with no
compile-time link between the two — exactly the kind of drift the branded-id
and shared-schema decisions elsewhere in this corpus (ADR-009, ADR-015) exist
to prevent. It remained the fallback for the one or two genuinely awkward
queries (the search index's `LIKE`-based matching in
`src/server/repositories/search-repository.ts`) where Drizzle's builder adds
ceremony without adding safety.

**Kysely.** A serious contender on paper — a pure query builder with strong
type inference and no schema-definition layer of its own — but it was passed
over because it would have meant hand-writing SQLite DDL for migrations with
no first-party migration generator, which the team judged riskier for a
project expecting frequent schema churn in its first two quarters.
